Executive summary

The most urgent availability risks are repeatable uploads without a storage quota, reading a drawing request fully into memory before enforcing its size limit, and generating daily PDFs from unbounded data in memory. Media deletion also crosses the database and filesystem without an atomic commit boundary.

How to read the percentages: Security percentages are subjective relative risk estimates for prioritization, combining exploitability and impact. They are not measured incident probabilities. Exposure changes with deployment controls, traffic, and account compromise.

HighSecurity65% relative risk

Repeated valid uploads can exhaust storage

A family member can upload separate valid images up to 10 MiB each. There is no account or family quota, upload rate limit, or automatic cleanup of unattached media in the reviewed code.

Trigger: an authenticated family member repeats uploads; impact depends on disk capacity and ingress controls.

Action: add a bounded storage quota, lifecycle cleanup for unused objects, and ingress rate limits; test quota races.

HighPerformance · Security45% relative security risk

Drawing size is checked after request allocation

The controller binds JSON to byte[]; only then does the validator reject bodies over 5 MiB. The multipart request setting does not cover this JSON endpoint.

Trigger: large or concurrent drawing PUTs by a permitted editor; heap pressure occurs before the 413 response.

Action: enforce a byte limit while reading the HTTP body, before binding it to an array.

HighPerformance

Daily PDFs accumulate unbounded data in memory

Report assembly walks every reading page and loads other daily sources. Rendering holds the PDF document and output in memory, then returns a complete byte array.

Trigger: data-heavy days or concurrent report requests; no load test established the failure threshold.

Action: set an explicit report budget, reduce embedded image size, and measure whether streaming or background generation is needed.

HistoryService.java:71–86 · DailyReportPdfRenderer.java:24 · HistoryController.java:44–53

High · conditionalArchitecture · Performance · QA

Media deletion spans a database transaction and filesystem I/O

The service deletes the file before its database transaction commits. A later commit failure could leave a database row referencing a missing file; slow storage also holds the row lock and connection longer.

Condition: a failure after external deletion or slow disk. This is a conditional integrity risk, not a reproduced failure. Existing tests cover normal deletion and in-use conflicts, but not a commit failure.

Action: design a recoverable pending-delete/after-commit flow with retry or compensation, then test commit failure. Preserve the existing pessimistic locking order.

MediaService.java:84–93 · PhotoMediaTests.java:221–244

MediumPerformance

Concurrent image validation has a substantial memory cost

Uploads are copied into byte arrays and decoded at up to 16,777,216 pixels. A full-size bitmap alone can occupy roughly 64 MiB, before input buffers and decoder overhead.

Trigger: several maximum-size uploads validated at once.

Action: set concurrency and pixel budgets from load tests, and monitor heap and upload latency.

MediaService.java:39–52 · ImageValidation.java:9–25, 125–148

MediumArchitecture

Media and photo records reach into each other's repositories

Both features access the other's persistence types; the media repository also queries photo and book tables. Rules or schema changes can require coordinated edits across features.

Effect: maintenance coupling and risk of bypassing a feature's own rules.

Action: expose focused operations from the owning services while preserving lock order; avoid a generic abstraction.

MediumSecurity35% relative risk

Existing access JWTs survive logout and password reset

Refresh tokens are revoked, but an already issued access JWT remains usable until its configured expiry, 15 minutes by default. This behavior is documented.

Condition: an attacker already holds a valid access JWT.

Action: if immediate revocation is required, check a server-side session or user version on protected requests.

Medium · conditionalSecurity30% relative risk

Authentication rate limits are process-local and IP-based

The fixed-window counter is held in one process and uses the remote IP. Several replicas do not share counters, while clients behind one proxy may share a bucket. The deployment documentation calls for coordinated ingress protection.

Condition: multiple instances, distributed requests, or shared source IPs without suitable edge controls.

Action: verify proxy identity and deploy a coordinated ingress limit; retain the bounded local limiter as defense in depth.

AuthRateLimitFilter.java:11–47 · authentication.md:451–455

Daily planning reads routine persistence details directly

The planning service uses routine repositories to assemble a read model. The intent is documented in code and does not appear to bypass a write rule, but it ties planning to the routine schema.

Condition: routine storage or mapping changes grow more complex.

Action: keep the current simple read path; if the integration expands, expose a focused routine-owned projection.

Low · potentialPerformance

Deep offset pagination can waste database work

Reading lists allow page offsets close to the integer limit. PostgreSQL still advances through skipped rows, so a very deep page may consume CPU and I/O even with a small response.

Condition: large histories or repeated deep page requests; no query plan or latency regression was measured.

Action: cap practical page depth, or use a cursor over the stable date and ID order if large histories require deep navigation.

ReadingService.java:54–56, 193–199 · ReadingSessionRepository.java:9–10

Low · potentialPerformance

Photo text and tag filters may become expensive

The history query searches a lowercase description by substring and computes a correlated tag count. Its cost may rise with family history size.

Condition: large photo histories with frequent text or tag searches; no execution plan or benchmark was collected.

Action: run EXPLAIN ANALYZE on representative data before considering a trigram index or query change.

What is working well

  • Nonpublic routes require authentication by default; JWT verification checks signature, issuer, audience, and expiry.
  • Family membership checks protect private resource access. Refresh and reset secrets are stored as hashes.
  • Feature packages follow responsibility-based subpackages; controllers generally delegate to services, and the history feature coordinates cross-feature reads without direct repository access.
  • Main lists use bounded pages; several responses batch related data; history queries have supporting indexes.

Suggested order of work

  1. Bound uploads by quota and lifecycle, and enforce drawing request size before allocation.
  2. Set a report generation budget and test memory under concurrent PDF requests.
  3. Make media deletion recoverable across storage and database failures.
  4. Reduce feature-to-feature repository access where it creates rule or schema coupling.
  5. Confirm production ingress rate limits and decide whether immediate JWT revocation is a product requirement.

Scope and confidence

Four agents independently reviewed the current checkout. Static findings identify reachable code paths and failure conditions, but deployment settings, production volume, query plans, load behavior, and real incident likelihood were not measured. The QA agent ran the full test suite, but did not start a separate HTTP server or run load and fault-injection tests. No authentication or cross-family access bypass was confirmed in the routes inspected. The architecture review found no need for a broad framework or service split.
